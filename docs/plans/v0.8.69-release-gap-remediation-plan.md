# v0.8.69 Pre-release Gap Remediation

Status: implementation-ready plan; no release tag is authorized by this document
Date: 2026-08-26
Baseline: `origin/main` at `2d1f3e7d5f6e3a44c6a6cbe301d1448bc7f6a0f2`
Current stable: `v0.8.68` at `40aae345531911da72f7d18d522ccf61575eedde`
Target: `v0.8.69`, beginning with the first unused `v0.8.69-rcN`

## 1. Decision and scope

Do not cut an RC yet. Complete the five serial PR phases below, require exact-head
and landed-main CI for each, then prepare the versioned release commit. The wallet
sync correctness work from PRs #949-#951 has no confirmed release blocker, but the
default launcher has a reproduced blocker and the remaining observability gaps
would leave the original address-history stall only partially diagnosable.

This plan closes every gap identified by the 2026-08-26 release-readiness audit:

| Gap | Severity before release | Owning phase |
| --- | --- | --- |
| MCP-disabled `start.sh` exits under `set -e` | Blocking | PR 1 |
| Release-tag upgrade gate never runs a real default-profile rebuild | Blocking | PR 1 |
| Active execution begins only at transaction processing | Required for this diagnostic release | PR 2 |
| Address-history, UTXO, gap-limit, repair, and enrollment stages are absent | Required for this diagnostic release | PR 2 |
| Strict worker diagnostics cannot safely gain stages during a rolling update | Required compatibility work | PR 2 |
| Incident script omits incremental claim/lease state and worker snapshot | Required operator evidence | PR 2 |
| Incident script exposes identifiers by default | Privacy hardening | PR 2 |
| No active-stage age gauge | Required hang detection | PR 2 |
| Wallet Sync dashboard and alerts omit the new metrics | Required operations surface | PR 3 |
| UI does not show live time in the current stage | Required user visibility | PR 3 |
| Changelog stops at v0.8.43 and omits #949-#951 | Release documentation | PR 4/5 |
| RC/stable failure recovery policy is inconsistent | Release safety | PR 4 |
| Release/pre-release commands contain stale unsafe instructions | Release safety | PR 4 |
| No affected-fleet RC canary contract or receipt | Release evidence | PR 4 and release execution |
| Package versions still identify v0.8.68 | Expected release preparation | PR 5 |

PR #947 is not part of this plan. It is an unrelated type-only dependency update
with failing CI and provides no runtime or diagnostic benefit to v0.8.69.

## 2. Cross-phase invariants

- Never report one overall wallet-sync percentage. Show a named stage, elapsed
  time, fixed-denominator counts only when actually known, and explicit terminal or
  retry state.
- Register an owned worker execution before preflight/network work. Every terminal
  path removes its active gauge and registry entry exactly once.
- Keep metric label domains closed. Never label or export wallet/user/job IDs,
  txids, addresses, lock keys/tokens, endpoints, hostnames, or raw error text.
- Keep support and incident output aggregate or pseudonymous by default. Raw local
  identifiers require an explicit on-box opt-in and never enter a shareable bundle.
- Preserve rolling compatibility. Existing candidate progress rows and diagnostics
  v1 remain parseable while new consumers explicitly negotiate execution snapshot
  v2. A request without the v2 selector must still receive the frozen v1 shape.
- The launcher fix must retain global `set -e`, optional-stack detection, offline
  protections, Postgres reconciliation, and additive MCP/monitoring/Tor behavior.
- One real MCP-disabled no-cache rebuild must be release-blocking, but it must run
  once per release gate rather than once for every historical upgrade fixture.
- Forgejo remains source of truth and CI authority; GitHub Actions remains disabled.
- Never delete or retarget a pushed tag. A failed RC gets a new RC number. A pushed
  stable tag with a code defect is abandoned in favor of a new patch release.
- Stable promotion requires the exact accepted RC commit, complete canary evidence,
  the stable tag's own install gate, and signed dual-provider publication evidence.

## 4. PR 2 — whole-pipeline stages, diagnostics, and incident evidence

### Progress contract

- Preserve `SyncProgressDetailsSchema` and `kind='sync_progress'` for the existing
  candidate-batch contract so old UI clients continue parsing it.
- Add a separate strict `SyncPhaseProgressDetailsSchema` with
  `kind='sync_phase_progress'`, fixed `stage_started`/`stage_completed`/
  `stage_failed`/`stage_aborted` events, bounded `elapsedMs`, and an optional strict
  `workItems: { completed, total, unit }` object for truthful known counts. Require
  `completed <= total`. `elapsedMs` is stage-local: it starts at the genuine stage
  transition, does not reset on a duplicate begin, and never means attempt age. Do
  not require fake batch numbers or imply a percentage.
- Define a closed execution-stage union covering:
  `preflight`, `initial_network`, `address_history`, `transaction_reconciliation`,
  the existing five candidate substages, `utxo_reconciliation`,
  `address_maintenance`, `missing_field_repair`, `subscription_enrollment`, and
  `finalization`. Map every default/quick pipeline phase to one of these names.
- Add a small shared phase-progress helper. Phase start and every terminal event
  must update logs and telemetry once, and candidate progress continues to own its
  finer batch stages. An execution has exactly one active stage:
  `transaction_reconciliation` owns transaction-phase setup, zero-candidate,
  inter-batch, and tail work; candidate substages temporarily supersede it and
  resume the parent after each candidate terminal event without overlapping gauges.

### Attempt lifecycle and metrics

- Add `beginStage`/`finishStage` to the attempt telemetry boundary and implement
  idempotent transitions in `WalletSyncAttemptTelemetry`.
- Immediately begin `preflight` after telemetry construction in
  `canonicalIncrementalSync.ts`, before `runSyncAttemptWithTimeout`. Instrument
  initial reachability/reset, pipeline stages, recursive gap scans, missing-field
  repair, subscription enrollment, and finalization.
- Extend the low-cardinality metrics stage domain and add
  `sanctuary_wallet_sync_active_stage_oldest_seconds{stage,mode,network}`. Track
  concurrent starts internally with opaque handles; clamp clock rollback and
  clean every gauge in terminal `finally` paths. A stage-start timestamp changes
  only on a genuine transition; duplicate/idempotent begin/finish calls must not
  refresh age and mask a hang.
- Extend stage-duration histogram buckets through the five-minute remote budget,
  its 30-second abort grace, the 30-minute maximum attempt boundary, and the outer
  1,830-second abort-grace edge so PR 3's p50/p95 panels do not collapse long
  stages into `+Inf`.

### Rolling diagnostics compatibility

- Freeze the existing v1 `byStage` record in the diagnostics protocol.
- Add request-negotiated wallet-sync execution snapshot v2 with the expanded fixed
  stages. Add an explicit `walletSyncExecutionVersion: 2` request selector; its
  absence continues to request v1 so old clients remain strict-parse compatible.
  New clients request v2, then on sequential `400` responses fall back to the
  current v1 execution request and finally the bare transport-v1 request. Parse
  the matching v2 or v1 response schema and classify unsupported/timeout/
  unavailable distinctly; a valid bare response proves transport reachability but
  classifies the wallet-execution snapshot as unsupported. The transport protocol
  can remain v1.
- Update the worker snapshot, execution registry projection, diagnostics client,
  notification support collector, strict schemas, and privacy tests. Keep all
  values bucketed and explicitly scoped to the sampled worker.

### Incident script

- Expand `scripts/diagnose-wallet-sync.sh` with incremental requested/claimed/

- Add an authenticated aggregate worker-snapshot section by invoking the built

- Extend log filters for typed stage starts/completions, budget expiry, fallback,

## 11. RC10 rejection and RC11 persistence remediation

RC10 is immutable and rejected. The exact candidate at
`5c1d1909f177b7bbd7c8f470da375b2de6bd0de3` passed its tag workflows and the
projection-only one-core replay, but failed after the affected host admitted the
retained 47-address wallet at `2026-08-29T00:39:00Z`.
This section supersedes Section 10's authorization and live-acceptance instructions
for RC10; they are retained only as historical evidence and must not be executed.

### Direct production evidence

- `preflight` completed in 3 ms, `initial_network` in 56 ms, and
  `address_history` completed all 47 addresses in 93,193 ms. The candidate then
  entered `persistence` after candidate, parent, timestamp, and classification
  stages completed.
- Worker readiness initially remained responsive, then three consecutive Docker
  health checks exceeded their 10-second timeout. Authenticated diagnostics also
  became unreachable and the backend reported degraded health.
- Worker memory grew from roughly 358 MiB before persistence to roughly 906 MiB
  while CPU remained near one full core. The worker exited with code 137 and
  `OOMKilled=true`; no container restart occurred.
- PostgreSQL retained the pre-attempt state after rollback: 169 transaction rows,
  zero input rows, two pre-existing output rows, and all 169 transactions with
  `ioComplete=false`. Exactly the first 25 repair cursors advanced immediately
  before persistence, matching `TX_BATCH_SIZE=25`. The generation, lease, and
  queued intent remain durable; no lock or evidence was manually deleted.

### Root cause and false-pass boundary

The RC10 gate was resource-shaped but not workflow-shaped. The compiled replay
called `fetchHistoriesPhase` and `fetchUtxosPhase`, asserted the in-memory compact

### RC11 implementation contract

1. Keep the candidate orchestration page at 25 and authenticated raw Electrum
   sub-batches at no more than 10, but decouple both from the persistence
   transaction size. Persist at most one Bitcoin transaction per fenced mutation.

   final `ioComplete=true` transition atomic for that transaction. A failure or

   `ADDRESS_SYNC_IO_UPSERT_MAX_ROWS=512`; derive its bind count from the larger

   ceiling and including negative decode results. Use bounded, set-based PostgreSQL
   upserts; do not retain whole-batch row graphs, duplicate derived address fields,
   clone classified arrays, or issue one update query per row.
   Before database selection, authenticate every history transaction into a
   separate compact envelope. It owns exactly one transferred canonical-byte
   buffer, its SHA-256 digest, scalar complexity, optional provenance-bound remote
   time/block metadata,

   indexes. It may not retain request hex, a parsed `bitcoin.Transaction`, decoded
   addresses, a full output array, repeated script strings, or one object per
   nonmatching output. Delete each remote batch source entry as its owned byte
   buffer is sealed. Bound source admission by the existing 64 Mi raw-hex-character
   ceiling and transferred/retained canonical bytes by its exact 32 MiB equivalent;
   assert the 2:1 conversion at the boundary. Retain the existing
   100,000-input, 600,000-output-scan, and 64 MiB script ceilings; wallet matches
   are unique indexes into the immutable context script dictionary rather than
   output objects. Worker tests must prove the compact response transfers one owned
   buffer instead of cloning it and that main retained state has at most one raw
   representation per txid.

   buffer into the worker and require the worker to return the identical buffer
   with its digest and derived result in one transfer response. Atomically restore
   envelope ownership before publishing full/outpoint evidence. A cancellation,
   worker error, or exit while ownership is transferred invalidates the envelope
   and terminates the attempt fail-closed; it never triggers a remote refetch.

   imply full materialization or exact-vout coverage. First union/deduplicate every
   current input `(parentTxid,vout)`, then authenticate parents with monotonically
   merged per-parent vout coverage. Later UTXO requests extract only their exact

   parent materialization. A no-op pass performs zero full materializations.

   after UTXO reconcile/insert or on terminal failure/cancellation; focused repeat
   tests must prove cleanup without relying on container exit.

   metadata only with its authenticated txid provenance, retain authenticated
   history height separately, and use the existing selected-candidate header
   fallback without treating missing raw time fields as compact-auth failure.

   authenticated address, amount, script, ownership, and output-type evidence.
   Derive output type only from the locked committed parent classification.
5. Retain the ordered parent-row and advisory locks, classification-address
   watermark, exact generation/token mutation fence, and post-commit effect
   boundary. Check the attempt abort signal before and after every chunk and set
   `ioComplete` only after all chunks and RBF work succeed. Perform one final
   abort/authority check immediately before the fenced callback returns and the
   database transaction may commit.

   ceilings. The structurally admitted/authenticated adversarial ceiling of 25,000
   inputs must not replace the output OOM with one large `OR` query, retained graph,
   or per-row update loop. Preserve the independent 25,000-input and 25,000-output
   ceilings, and add an exact authenticated maximum of 4,000,000 weight units,
   computed with the parsed transaction's exact serialized `weight()` semantics.
   Enforce it immediately after raw parsing/authentication and before input/output
   projection, cache insertion, worker response/structured clone, or repository

   to exclude.

   evidence authentication, evict evidence needed by later UTXO reconciliation,
   parallelize persistence, or split one transaction across independently
   committed fences. Do not move history membership behind database selection,
