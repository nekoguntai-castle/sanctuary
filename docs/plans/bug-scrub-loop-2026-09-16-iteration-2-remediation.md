## Phase 3 — pending approvals include wallets where the role comes from a group (server, P2)

Finding: `approvals-pending-list-ignores-group-approver-role`.

Evidence: `server/src/api/approvals.ts:26` and `server/src/assistant/tools/approvalReadTools.ts:54` resolve approve-capable wallets with `walletSharingRepository.findWalletIdsByUserRole(userId, [...WALLET_APPROVE_ROLE_VALUES])`, which queries `prisma.walletUser` only (`walletSharingRepository.ts:171-183`). Contract: `findWalletIdsByUserRole(userId, roles)` returns the union of (a) wallet ids from `walletUser` rows with `role in roles` (unchanged) and (b) wallet ids from `prisma.wallet.findMany({ where: { groupRole: { in: roles }, group: { members: { some: { userId } } } }, select: { id: true } })`, de-duplicated, MINUS any wallet id that has a `walletUser` row whose role is not in `roles`. Including that wallet in the pending list without the subtraction would surface a request the same user cannot actually vote on, trading one bug for a more visible one. Both callers are unchanged.

## Phase 5 — operator recovery labels a halted-after-success run as partial (ownership tooling, P2)

Finding: `operator-recovery-session-refused-after-success-terminal-outcome-rejected`.

Evidence: `scripts/ownership/cleanup-action-runner.mjs:439-441` sets `terminalState` to `stopped?.result` (e.g. `refused`) whenever the run did not complete every action, regardless of earlier successes; `scripts/ownership/operator-recovery-session.mjs:14-19` maps that straight to the receipt state and `:95-108` writes it as `terminalOutcome`; `scripts/ownership/cleanup-journal-protocol.mjs:263-272` computes `partial` for a result set with some successes and some non-successes and `:274-282` `handleTerminal` throws `cleanup journal terminal outcome is inconsistent with action results` on mismatch. A recovery approval that cleans one resource and then halts on a refusal therefore wedges: every re-run rebuilds the same mismatch.

Contract: `operator-recovery-session.mjs` must stop hand-deriving the label from the runner's stop reason and instead reuse the already-exported, already-tested pure helper `executionTerminalOutcome(results, recovered = false, cancelled = false)` from `cleanup-execution.mjs:61-70` — it implements exactly the protocol's `terminalOutcome` rule (`cleanup-journal-protocol.mjs:263-271`: `ambiguous` if any result is `ambiguous`; `cancelled` if `cancelled` or any `failureClass === 'cancelled'`; `results.length === 0` → `cancelled`/`recovered`/`no_op`; all successful (`cleaned`/`absent`/`retained`) → `recovered`/`cleaned`; some successful → `partial`; none successful and all `refused` → `refused`; otherwise `partial`) and is already reused this way by `cleanup-recovery.mjs:180,213,221` (`executionTerminalOutcome(results, true, journal.protocol.cancellationSeen)`). Replace the local `terminalState(result, recovered)` function's body with a call to `executionTerminalOutcome(result.results, recovered)` — the session has no `journal.protocol.cancellationSeen`-style flag to pass as the third argument, and none is needed: the helper's own `results.some((entry) => entry.failureClass === 'cancelled')` check already covers a cancellation surfaced through an action result, which is the only way the session observes it. This reuses the one correct implementation instead of adding a third copy of the rule, so the runner's own `terminalState` field is left untouched as its own internal stop-reason signal. Add `import { executionTerminalOutcome } from './cleanup-execution.mjs';` to `operator-recovery-session.mjs` (no cycle: `cleanup-execution.mjs` does not import `operator-recovery-session.mjs`, and both already sit alongside `cleanup-action-runner.mjs` in `scripts/ownership/`). `cleanup-execution.mjs:246,413` and `cleanup-recovery.mjs:193` already call `executionTerminalOutcome` (directly or via a `state` variable it produced) and need no change — this closes the loop the earlier draft of this contract left open.
