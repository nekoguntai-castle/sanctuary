## Phase 1 — LabelManager resets its draft synchronously when the wallet changes (frontend)

Finding: `label-manager-draft-leaks-across-wallet-switch`.

Evidence: `src/components/LabelManager/useLabelManagerController.ts:24-29` holds `isCreating`, `editingLabel`, `formName`, `formColor`, `formDescription`, `deleteConfirm` in plain `useState` with nothing keyed on `walletId`; `:65-77` `handleSave` reads the current `walletId` prop together with the stale `editingLabel`/form values. `src/components/WalletDetail/tabs/SettingsTab.tsx:67` renders `GeneralSettings` without a `key`, which at `tabs/settings/GeneralSettings.tsx:99` renders `LabelManager` (also without a `key`); `src/app/routeDefinitions.tsx:92` maps every `/wallets/:id` to one element and `useWalletDetailController.ts:42` reads `useParams`, so a wallet switch reuses the mounted subtree. Sibling panels reset on wallet change (`tabs/settings/WalletRemediationPanel.tsx:64-71`, `WalletTelegramSettings/useWalletTelegramSettingsController.ts:40-55`); LabelManager does not. Result: an open create draft is saved under wallet B (silent wrong-wallet label); an open edit draft yields 404 because `labelService` scopes `findByIdInWallet(labelId, walletId)`.

Contract: the controller tracks the wallet it was rendered for and, the moment `walletId` differs, resets the form (`isCreating`, `editingLabel`, `formName`, `formColor` to `PRESET_COLORS[0]`, `formDescription`) and `deleteConfirm` synchronously during render, mirroring `src/components/DraftList/useDraftListController.ts:66-76` (`trackedWalletId` pattern) rather than an effect, so the stale draft is never painted under the new wallet. Mutation errors are also reset (`createMutation.reset()`, `updateMutation.reset()`, `deleteMutation.reset()`) so wallet A's save error is not shown on wallet B; those are external hook side effects, so call them from a `useEffect([walletId])` that skips the initial mount, not during render. A save already in flight when the wallet switched still completes against the wallet it was issued for (`mutateAsync` captured `walletId` at call time); `handleCancel`/`onLabelsChange` afterwards only touch local form state and the parent's refresh callback, so no cancellation is attempted. The labels list itself already refetches via the query key. No view or type change is required (`LabelManagerController` shape unchanged).

## Phase 2 — HTTP metrics path label is bounded (server)

Finding: `http-metrics-path-label-unbounded-cardinality`.

Evidence: `server/src/index.ts:168` mounts `metricsMiddleware()` globally, before route registration and before any authentication; the coarse rate limiters at `index.ts:114-136` cover only `/api` and `/internal` (default 1000 req/min/IP, `config/envSections.ts:37`). `server/src/middleware/metrics.ts:78` computes `path = pathNormalizer(req.path)` before routing and `:107-108` records `{ method, path, status }` on every response, including 404s. `server/src/observability/metrics/helpers.ts:23-33` `normalizePath` rewrites only UUID, numeric, Bitcoin-address and 64-hex segments and passes every other segment through verbatim; every other module in `server/src/observability/metrics/*.ts` normalizes labels to a fixed enum with an `'other'` fallback. Series live in the process-wide prom-client registry (`metrics/registry.ts`) and never expire. Any client can therefore mint one permanent series per distinct unmatched path, growing process memory and the Prometheus index without bound.

Contract (all in `server/src/middleware/metrics.ts` plus a helper in `server/src/observability/metrics/helpers.ts`; no metric names or label names change, so dashboards keep working):
1. The label is decided at response time, inside the `res.end` wrapper where `res.statusCode` is known: a 404 response is labeled `/:unmatched` regardless of the requested path (the `notFoundHandler` is the only producer of 404 for unrouted paths; routed handlers that legitimately return 404 for a missing object collapse too — acceptable, the method+status still distinguishes them, and the previous per-object path would already have been normalized to `:id`).
2. Segment-level bounding in `normalizePath`: after the existing rewrites, any path segment that is not a short safe token (`^[A-Za-z0-9._~-]{1,64}$`) is replaced with `:other`. This keeps `/api/v1/wallets/:id/transactions` intact and collapses percent-encoded, over-long, or exotic segments.
3. A hard cap as the actual bound: the middleware keeps a per-process `Set` of distinct normalized path labels it has emitted; once it holds `MAX_DISTINCT_HTTP_PATH_LABELS` (500, a constant with a comment; the current route table is well under 300 templates) any further new path is recorded as `/:other` and a single `log.warn` is emitted the first time the cap is hit. The cap applies after rules 1–2, so 404s never consume cap entries. Export `resetHttpPathLabelCache()` from `server/src/middleware/metrics.ts` and call it explicitly alongside `metricsService.reset()` in tests — do not wire it into `MetricsService.reset()` in `server/src/observability/metrics/registry.ts`: that module is imported (via the `observability/metrics` barrel) by `middleware/metrics.ts`, so having `registry.ts` import back into `middleware/metrics.ts` to clear the cache would create a circular import.
4. `excludePaths` behavior is unchanged.
5. (Added during implementation, from the pre-commit architecture review.) Only a successful (`statusCode < 400`) or server-error (`>= 500`) response may admit a new path into the cap set; a 5xx proves the request reached a real route (an unrouted path can only 404), so per-route error visibility survives a restart during an incident. `apiVersionMiddleware` (`server/src/index.ts:174`) answers 400/410 for `/api/v99/<anything>` before routing, and CSRF 403 / rate-limit 429 / auth 401 likewise precede any handler, so without this rule ~500 unauthenticated requests to distinct junk paths would fill the first-come cap and push every later legitimate route into `/:other` until restart. A rejected request on a never-admitted path is labeled `/:other`; an already-admitted path keeps its real label for every status. Also from that review: `normalizeSegment` tests the 64-hex txid shape before the Bitcoin-address shape so a txid beginning with `bc1` is `:txid`, and `middleware/metrics.test.ts` pins the `/:unmatched` and `/:other` labels through its mocked counter and calls `resetHttpPathLabelCache()` in `beforeEach`.

Failing tests first (red against `origin/main`), both in `server/tests/unit/observability/metrics.test.ts` (not `middleware/metrics.test.ts` — see below):
- 50 requests to distinct random paths that all resolve 404 produce exactly one `sanctuary_http_requests_total` series (`{method:'GET', path:'/:unmatched', status:'404'}`) — today 50; a matched route (`/api/v1/wallets/<uuid>`) still records `/api/v1/wallets/:id` with its real status; after the cap is reached, a new 200 path records `/:other` and the warn is logged once.
- `normalizePath('/api/v1/%E2%9C%93/x'.repeat(2))` and a 200-character segment normalize to `:other`; existing recognized-shape assertions unchanged.

No test in the repo today reads series counts via `defaultRegister.getSingleMetric(...).get()` — that pattern does not exist and must not be assumed. `server/tests/unit/middleware/metrics.test.ts` module-mocks `../../../src/observability/metrics` wholesale (`httpRequestsTotal` is `{ inc: mockInc }`, a bare spy with no real Counter/registry behind it), so the 50-distinct-404-paths series-count assertion cannot be added to that file's existing mocked `describe` blocks.
