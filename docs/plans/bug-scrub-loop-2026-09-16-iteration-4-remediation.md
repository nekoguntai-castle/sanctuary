## Phase 1 — Keystone parsers derive purpose and script type from parsed path components (frontend, P2)

Finding: `keystone-scriptpath-substring-misclassification`.

Evidence: `src/services/deviceParsers/parsers/keystone.ts:69-72` `getKeystoneAccountPurpose` returns `MULTISIG` when the raw path contains `48'`/`48h` anywhere; `:74-83` `getKeystoneScriptType` returns `NESTED_SEGWIT` when a purpose-48 path contains `/1'`/`/1h` anywhere (`:76`) — which matches the account-index component of `m/48'/0'/1'/2'` (second native-segwit multisig account) or the coin-type component of `m/48'/1'/0'/2'` (testnet) — and, for single-sig, checks `86'` before `49'` before `44'` by substring, so `m/44'/0'/86'` (legacy, account 86) is reported as taproot. `:193-197` `keystoneMultisigParser.parse` repeats the `/1'` test and defaults to native segwit. Both parsers are registered independently of the manual-import path (`src/services/deviceParsers/index.ts:47-48,61-62`), so the iteration-1 fix in `src/components/DeviceDetail/accounts/accountImportUtils.ts:108-125` (`createSingleAccount` → `parseDerivationPath`) does not cover them. A wrong script type on an imported cosigner account drives the wallet to expect a different address format than the device signs for. `tests/services/deviceParsers/keystone.branches.test.ts` uses only account index 0 and coin type 0 (`:41-49,:83-84,:124,:176,:195,:200`), so the collision is never exercised; `tests/services/deviceParsers/deviceParsers.test.ts:106-119,:147-171,:246-255` likewise use `m/48'/0'/0'/{1,2}'` only.

Contract (all in `src/services/deviceParsers/parsers/keystone.ts`):
1. Import `parseDerivationPath` from `@sanctuary/shared/utils/bitcoin` and `isWalletScriptType` from `@sanctuary/shared/constants/walletIdentity` (the file already imports `DeviceAccountPurpose` and `WalletScriptType` from the latter). Replace `getKeystoneAccountPurpose` and `getKeystoneScriptType` with one helper, `classifyKeystonePath(path: string): { purpose: DeviceAccount['purpose']; scriptType: DeviceAccount['scriptType'] }`, that calls `parseDerivationPath(path)` once and returns `purpose: parsed.purpose === 48 ? DeviceAccountPurpose.MULTISIG : DeviceAccountPurpose.SINGLE_SIG` and `scriptType: isWalletScriptType(parsed.scriptType) ? parsed.scriptType : WalletScriptType.NATIVE_SEGWIT` — byte-for-byte the mapping `createSingleAccount` uses, so the two import paths cannot drift again.
2. `createKeystoneAccount` (`:85-96`) spreads the helper result instead of calling the two removed functions.
3. `keystoneMultisigParser.parse` (`:193-197`) replaces the inline `/1'` test with `classifyKeystonePath(derivationPath).scriptType`; `purpose` stays the literal `MULTISIG` (the multisig format is multisig by definition). The `normalizeKeystonePath`/`replace(/^M/, 'm')` normalisation stays as-is (`parseDerivationPath` also normalises, so both `M/…` and `m/…` inputs behave identically).
4. Behaviour parity for every existing fixture: `m/44'/…` → legacy, `m/49'/…` → nested, `m/84'/…` → native, `m/86'/…` → taproot, `m/48'/0'/0'/1'` → nested, `m/48'/0'/0'/2'` → native, `m/48'/0'/0'/3'` → `"unknown"` → native fallback (today: native), `''` → purpose `null` → single-sig + native (today: the same).
