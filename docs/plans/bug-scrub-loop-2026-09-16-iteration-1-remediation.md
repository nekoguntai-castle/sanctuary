## Phase 1 — `get_balance_history` accumulates satoshis as real integers (server, P1)

Finding: `assistant-balance-history-decimal-bigint-string-concat`.

Evidence: `server/src/repositories/transactions/core.ts:305-356` `getBucketedBalanceDeltas` runs four `$queryRaw` variants selecting `COALESCE(SUM("amount"), 0) AS amount` and declares the row type `{ bucket: Date; amount: bigint }`. PostgreSQL's `SUM(bigint)` is `numeric` (confirmed on the local stack: `SELECT pg_typeof(COALESCE(SUM(x),0)) FROM (SELECT 1::bigint AS x) t` → `numeric`), and `@prisma/client` 7.8.0's raw-result deserializer maps `decimal` columns to `Prisma.Decimal` (`node_modules/@prisma/client/runtime/client.js`: `case "decimal": return new Decimal(t)`), never to `bigint`. `server/src/assistant/tools/analyticsReadTools.ts:164-171` seeds `cumulativeFromStart = BigInt(0)` and does `cumulativeFromStart += bucket.amount`; `BigInt + Decimal` goes through `ToPrimitive` → `Decimal#valueOf()` (a string), and `+` with a string operand concatenates (`node -e` repro with `decimal.js`: `"0100"`, then `"0100-25"`). Every `get_balance_history` response for a wallet with transactions therefore carries a garbage `cumulativeDeltaSats`. The sibling caller `server/src/api/transactions/crossWallet.ts:387-389` uses `-=`, which coerces numerically, so the chart endpoint is unaffected. `server/tests/unit/assistant/readToolExecutors.test.ts:394-411` mocks the repository with `100n`/`-25n`, i.e. the declared type rather than the runtime type, which is why the suite is green.

Contract:
1. `getBucketedBalanceDeltas` casts the aggregate in all four queries: `COALESCE(SUM("amount"), 0)::bigint AS amount`, so PostgreSQL returns `int8` and Prisma deserializes a real `bigint`; the declared row type becomes true.
2. `balanceHistoryTool` no longer trusts the declared type at the seam: accumulate with a small local helper `toSatoshiBigInt(value: bigint | number | string | { toString(): string })` that returns `typeof value === 'bigint' ? value : BigInt(String(value))` (a `Decimal`, a numeric string, or an integer number all convert exactly; `BigInt(String(...))` throws on a non-integer string, which is the correct failure for a corrupt aggregate). `deltaSats` is derived from the converted value too, so both fields agree.
3. No response field, metric, or schema changes; `deltaSats`/`cumulativeDeltaSats` stay decimal strings.

Failing tests first (red against `origin/main`):

Today: `'0100'`/`'0100-25'`.

## Phase 3 — webhook retry backoff multiplier is floored at 1 (server + form, P2)

Finding: `webhook-backoff-multiplier-unvalidated`.

Evidence: `server/src/services/webhooks/config.ts:22-28,50-52` `getRetryConfig` → `getPositiveNumber(retryConfig.backoffMultiplier, 2)` accepts any finite value `> 0`; `deliveryService.ts:300-309` `calculateRetryDelay` = `initialDelayMs * multiplier^(attempt-1)` capped only above by `maxDelayMs`, with up to `endpoint.maxAttempts` attempts (`:243-251`). Contract:
1. Server: `getRetryConfig` uses a new `getNumberAtLeast(value, minimum, fallback)` for `backoffMultiplier` with minimum `1` (a stored `0.5`/`0`/`NaN` falls back to `2`; `1` and `1.5` are kept). `initialDelayMs`/`maxDelayMs` keep `getPositiveNumber` (unchanged behaviour). `calculateRetryDelay` therefore never shrinks below `initialDelayMs`.
2. Form: `clampNumber` (`webhooks/model.ts:175-179`) rounds via `Math.round(parsed)` — confirmed, it is not float-preserving. Add a new `clampFloat(value: string, min: number, max = Number.MAX_SAFE_INTEGER)` beside it (same signature and NaN→`min` fallback, but `Math.min(max, Math.max(min, parsed))` without rounding) rather than changing `clampNumber`'s rounding behaviour, which its other callers (the ms-valued `DelayField`s) rely on. Route the Backoff `onChange` through `clampFloat(String(event.target.value), 1)` so `1.5` stays `1.5` (required by the existing assertion in `WalletWebhookForm.test.tsx:124-128`, which already expects `retryBackoffMultiplier: 1.5`) and an empty/NaN input clamps to `1`.
