## Delivery group C — payjoin two-round BIP78 signing (PR C, after B; decision D-5)

### Context the phases rely on (re-verified at 2524b862)

**BIP78 requirements** (bip-0078.mediawiki):
- **Protocol, Original PSBT:** the original must have all witnessUTXO/nonWitnessUTXO filled in, be finalized, leave out global xpubs and keypaths, and be broadcastable.
- **Receiver's original PSBT checklist:** non-interactive receivers must check that the original is broadcastable. Receivers without a full node may broadcast the original themselves after a 1-minute timeout.
- **Receiver's payjoin proposal:** the receiver uses every original input, finalizes only its own added inputs, and fills UTXO data only for those added inputs.
- **Senders' payjoin proposal checklist:**
  - Absolute fee is at least the original's; version and locktime are unchanged; sender sequences are unchanged.
  - No input has keypaths or partial signatures.
  - Sender inputs are **not** finalized and do **not** specify witness_utxo/non_witness_utxo. Receiver inputs **are** finalized and carry witness_utxo or non_witness_utxo.
  - The proposal does not introduce mixed input script types.
  - All proposal inputs use the same sequence. Every original sender input is present.
  - No output has keypaths. Sender outputs are preserved, and value-decrease rules apply.
  - The sender then re-signs **only** the inputs that were in the original.
- **Optional parameters:** `disableoutputsubstitution`, `maxadditionalfeecontribution`, `minfeerate`.

### Decisions (conservative defaults; flagged for the user)
- **C-D1 — round-one failure.** If the attempt fails (receiver error, invalid proposal, timeout, abort, or a C-D8 403 `payjoin_policy_usage_unsupported`), Sanctuary releases the original (C4) and broadcasts the signed original automatically. The user already clicked Broadcast, and this matches today's silent fallback.
  - *Alternative:* ask first.
- **C-D2 — round-two exit.** The proposal panel offers "Sign payjoin" and "Send without payjoin" (release, then broadcast the original).
  - Closing or navigating away broadcasts **nothing**. It only does a best-effort release of the original, and the panel warns that the receiver may still broadcast the signed original (BIP78 1-minute receiver timeout).
  - Closing the tab does not unmount React, so no release runs: the original stays superseded and the proposal intent stays `ready` until it expires (24h, `service.ts:29`). There is no funds risk (the server never lets both broadcast, and C-D8 guarantees no enforce-mode usage window applies to a wallet that reached `/attempt`); the receiver may still broadcast the original. No `pagehide`/`keepalive` handler is added.
  - No client-side auto-timer.
- **C-D3 — eligibility.** Payjoin is attempted only when all of these hold:
  - the wallet is single-sig with a **native segwit (P2WPKH) or taproot** script type (with the C-D4 peer rule and the C-D10 mixed-type rule, no other sender type can ever complete, so it must not send its signed original for nothing);
  - it is not draft mode, and no draft is bound to the intent;
  - the send is not approval-required;
  - there is exactly one output;
  - round one came from an **uploaded/QR signed PSBT**. USB-signed sends skip payjoin (status `skipped`), and round two is never routed to a connected device, because the Ledger, BitBox and Trezor adapters all finalize every input.
  - The server independently refuses multisig, non-P2WPKH/P2TR (`signingContext.scriptType`, 400 `payjoin_script_type_unsupported`) and draft-bound intents.
- **C-D4 — peer input trust (coordinator).** The server does not verify the receiver's input witness cryptographically. It requires all of the following:
  - the peer input's prevout script is **P2WPKH or P2TR only**; any other peer script type is rejected at `/attempt`, which falls back to the original;
  - the peer input is finalized at `/attempt`, with an empty or absent `finalScriptSig` (an empty one is stripped before the proposal intent is persisted, C3 step 12; a non-empty one is rejected), and its real weight does not exceed the per-type maximum the fee-policy estimate uses (else rejected at `/attempt`, falling back);
  - the node authenticates its prevout (existing `authenticateIntentPrevouts`);
  - the peer outpoint is not a wallet UTXO;
  - at broadcast, the candidate's peer final fields are absent or byte-equal to the stored ones; the server re-attaches the stored ones.
  - An invalid peer witness is a node `mandatory-script-verify-flag` definite rejection. That releases the claim to `ready` and the client falls back.
  - *Alternative:* verify P2WPKH and P2TR key-path peer witnesses locally.
- **C-D5 — protocol options.**
  - The sender adds `disableoutputsubstitution=true`, because the validator already forbids substitution.
  - It sends no `maxadditionalfeecontribution`, so the receiver may not reduce our outputs (already enforced).
  - A proposal that adds no receiver input is rejected and handled as a fallback.
- **C-D6 — round-two PSBT shape.** The device receives the proposal with the peer input's `finalScriptWitness` stripped and `witnessUtxo` kept. The stored intent PSBT keeps the receiver's final fields, and the server re-attaches them (C1).
- **C-D7 — UX copy before round one.** When payjoin is eligible, the review step says: "The receiver supports payjoin: you will sign twice. Your first signature authorizes this exact payment and is shared with the receiver as a fallback." No extra consent checkbox.
- **C-D8 — policy before the original leaves the server (coordinator, conservative; replaces the review-9-pass-1 "payjoin hold").** A receiver may broadcast the original (BIP78), and Sanctuary would then never reserve its policy usage. The earlier design stored a reservation "hold" in `broadcastMetadata` on the `ready` original; the database refuses that (`transaction_signing_intents_broadcast_state_check`, migration `20260810180000_add_signing_intent_broadcast_claims/migration.sql:26-38`: a `ready` row must have NULL `broadcastMetadata`; pinned by `signingIntent/migration.test.ts:25`), and migrations are forbidden. So `/attempt` instead **refuses payjoin with 403 before the signed original leaves the server** whenever either holds:
  - (i) the original needs approval: an enforce-mode `approval_required` trigger, or any blocking policy (the existing preview evaluation `assertPayjoinNeedsNoApproval`, `payjoin.ts:293-307`, kept), or the intent is draft-bound (409 `draft_bound_intent`, C-D3); the policy evaluation exists today, while the draft-bound check is new (the `/attempt` handler, `payjoin.ts:314-412`, has no draft check at HEAD; C3 step 2 adds it);
  - (ii) **any enforce-mode policy that would reserve usage** applies to the wallet: exactly the set `reserveEnforcedUsage` → `reservePolicyWindows` reserves (`policyEvaluationEngine.ts:462-494,512-590`), i.e. an active non-`monitor` `spending_limit` with a `daily`/`weekly`/`monthly` limit > 0, or an active non-`monitor` `velocity` with `maxPerHour`/`maxPerDay`/`maxPerWeek` > 0 (policies from `getActivePoliciesForUsage(walletId)`: wallet, group and system policies, `policyEvaluationEngine.ts:440` (`:133` is `getActivePoliciesForWallet`); a `spending_limit` with only `perTransaction` reserves nothing and is checked by the evaluation in (i)). Reason **`payjoin_policy_usage_unsupported`**, message "Payjoin is not available while a spending-limit or velocity policy is enforced on this wallet".
  - The client treats the 403 like any round-one failure (C-D1): release (returns `not_superseded`), then a **normal broadcast of the signed original**, which evaluates and reserves exactly once through the unchanged `reservePolicyUsage`. So no double count and no unreserved Sanctuary broadcast. No hold, no `broadcastMetadata` write on any `ready` row, no `findHeldPolicyReservations` branch, no new usage storage, and `api/transactions/broadcasting.ts` is not changed by group C.
  - Residuals (recorded): a receiver that broadcasts the original itself skips **monitor-mode** usage recording (`recordMonitorUsage`, display only; enforce-mode cannot be skipped because (ii) refused). A policy added between `/attempt` and a receiver broadcast is not reserved (time-of-check window of seconds). A proposal broadcast by Sanctuary reserves its net spend P−r normally.
  - *Alternative (not taken, needs a user decision):* keep a hold outside the intent row (e.g. a `SystemSetting` row keyed `payjoin-hold:<originalIntentId>`).
- **C-D9 — no drafts during the flow (coordinator).** Saving a draft bound to a payjoin replacement intent (`source === 'payjoin'`) or to an original that a payjoin proposal was minted from is refused with **409 `payjoin_intent_not_draftable`**, and the client disables Save draft while the payjoin status is `negotiating`, `awaiting-signature` or `broadcasting`. The original marker is the supersession linkage, not a hold: while superseded, the original already fails `loadSigningIntent` with 400 `stale_intent` (`service.ts:139`); after `release-original` restores it, the replacement row's `supersededById` points at the original (C4 step 3), so "a `source:'payjoin'` intent whose `supersededById` is this intent" marks it. Residual: an original whose `/attempt` failed before a proposal was minted (receiver error, refusal, timeout) carries no marker and stays draftable server-side; the client never saves it (it falls back to broadcast), and such a wallet has no approval policy (C-D8 (i)). This also resolves the C-D6 hash mismatch (the stripped response PSBT can never match the stored replacement hash at draft create).
- **C-D10 — BIP78 deviation and mixed input types (coordinator).** Deviation, recorded: BIP78 says proposal sender inputs must not carry witness_utxo/non_witness_utxo; Sanctuary **accepts** them when byte-equal to the original's and rejects any that differ (restoration copies the original's either way, so accepting equal data cannot change what is signed). Mixed-type rule: every receiver input's prevout script type must equal the sender inputs' script type (all P2WPKH or all P2TR); otherwise the proposal is rejected and the flow falls back.
- **C-D11 — client timing (coordinator, C5).** The client gives `/attempt` 75s (`timeoutMs: 75_000`), above the server's 30s receiver budget (`sender.ts:22`) plus validation; on any round-one failure it always calls release and lets the server decide. If the fallback broadcast then fails **for any reason**, it calls release once more and retries the original broadcast exactly once **only if that release returns `restored: true`** (the server persisted a proposal after the client gave up). The retry is server-decided, not reason-decided, because the late persist surfaces in two forms: 400 `stale_intent` when it lands before the broadcast's `loadSigningIntent`, and 400 `metadata_mismatch` when it lands after validation but before `claimBroadcast` (the claim's `updateMany` fails on `supersededById: null` → repository `conflict`, `transactionSigningIntentRepository.ts:195-200` → `metadata_mismatch`, `signingIntent/broadcastLifecycle.ts:105-107`; the window spans prevout authentication, canonical metadata and `reservePolicyUsage`, `api/transactions/broadcasting.ts:481-511`).

### Phase C1 — Accept receiver-finalized `payjoin_peer` inputs in signed-artifact validation (P2, `signed-artifact--payjoin-peer-input-finalized-rejected`)

| From | Trigger | To | Effect |

| `broadcasting` | broadcast returns `true` | `success` | Done. |
| `broadcasting` | broadcast returns `false` (it never throws) | `failed` or stays | Always release and let the server decide; never infer failure from the boolean. `restored:true\|false` (the proposal never reached `claimed`, e.g. a definite rejection, or the original was already restored) → broadcast the original with "Sent without payjoin" (with the one release-decided retry). 409 (the proposal outcome is unknown or it was accepted) → "Broadcast pending reconciliation", **never** broadcast the original. |
| `awaiting-signature` | reset, identity change, or unmount | `idle` | Best-effort release (log on failure, mirroring `useSendTransactionActions.ts:456`), reading the status ref and using the release's own `AbortController`. Broadcast nothing (C-D2). |

## Phase C7 — Findings exposed during implementation review (added 2026-10-20)

The adversarial implementation review of C1–C6 exposed one new blocking finding inside this delivery boundary, plus three P3 hardening items in the same files. Per the loop contract they are folded into this PR instead of deferred.

- **`payjoin-proposal--receiver-controlled-sighash` (P2):** a BIP78 receiver can set `PSBT_IN_SIGHASH_TYPE` (for example NONE, or SINGLE|ANYONECANPAY) on a sender input. No layer rejects it, and `validatePresentSignatures` accepts a signature over whatever hash type it carries. Fix: the proposal checklist rejects any input whose `sighashType` is set to anything other than ALL (DEFAULT for P2TR). As defence in depth, `validatePresentSignatures` rejects non-ALL/DEFAULT partial signatures for every intent, after confirming no legitimate flow produces one. Each change gets a fail-first test.
- **P3 items, fixed alongside:**
  - `payjoin-attempt--draft-binding-toctou`: re-check the draft binding inside the supersede transaction.
    - Residual (follow-up): the draft side never locked the intent row, so the re-check could not serialize against it (a draft inserted between `assertIntentDraftable` and its insert could bind a just-superseded original). Draft creation now inserts the draft in one transaction that first row-locks the intent with a no-op conditional write (`lockDraftableIntent`: `id`, `walletId`, `supersededById: null`, `source != 'payjoin'`); a count of 0 is the typed 409 `payjoin_intent_not_draftable`. Whichever writer locks the row first wins: a supersession that commits first leaves nothing to lock, and one that runs second waits for the draft's commit and its re-check sees the draft. No migration. Fail-first: `payjoinTwoRound.fallback-drafts.contracts.ts` holds a draft insert after its intent check and runs round one against it; on the old code it ended with a draft bound to a superseded original.
  - `payjoin-attempt--replacement-accepted-as-original`: refuse `source === 'payjoin'` originals with a typed 409.
  - `payjoin-sender--no-minfeerate`: send `minfeerate` and reject proposals that fall below it.
- **Review hardening:**
  - Round two refuses a candidate whose unsigned txid differs from the proposal's.
  - The proposal broadcast sets busy synchronously.
  - One C6 scenario runs real prevout authentication, with only the node client stubbed.

**Acceptance:** every item has a fail-first test. The critical mutation shards and the six wallet-safety profiles are re-proven after any re-pin of `artifactValidation.ts`.
